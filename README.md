# Novatek Electro EM-12x для Home Assistant

Кастомная интеграция Home Assistant для счётчиков-ограничителей электроэнергии
Novatek Electro **EM-129** (Web API также совместим с EM-125 / EM-126T — проверено
на EM-129, `device_id` остальных моделей распознаётся автоматически).

- Home Assistant Core **2026.11.2** (минимальная версия 2024.11)
- Протокол: локальный Web API v1.2 поверх HTTP, класс IoT: `local_polling`
- Проверено на реальном устройстве: все команды чтения и записи, включая реле,
  сбросы журналов и перезагрузку

---

## Поддерживаемые модели

| Модель | Статус |
|---|---|
| **EM-129** | Полностью протестировано на реальном приборе (прошивка `1.271.3.34`) |
| EM-125 / EM-126T | Протокол общий (та же спецификация Web API), модели распознаются по `device_id`, **но не тестировались** |

⚠️ **Важно про авторизацию.** Пароль хешируется как
`SHA1(префикс модели + пароль + соль)`. В коде префикс задан константой
`LOGIN_PREFIX = "EM-129"`. Для EM-125/EM-126T префикс, вероятно, другой
(`"EM-125"` / `"EM-126T"`), поэтому вход на этих моделях может не работать.
Если нужна поддержка — пришлите лог/`device_info` с прибора, вынесу префикс
в настройку (config flow).

## Установка

### Вручную

1. Скопируйте папку `custom_components/novatek_em12x` в каталог конфигурации HA:

```
<config>/
└── custom_components/
    └── novatek_em12x/
        ├── __init__.py
        ├── manifest.json
        └── ...
```

2. Перезапустите Home Assistant.
3. **Настройки → Устройства и службы → Добавить интеграцию** → найдите
   «Novatek Electro EM-12x».

### HACS

1. HACS → ⋮ → Custom repositories → добавьте URL этого репозитория,
   категория **Integration**.
2. Установите «Novatek Electro EM-12x», перезапустите HA.

## Первичная настройка

Мастер запросит:

| Поле | Описание |
|---|---|
| **Адрес устройства** | IP или hostname, например `192.168.75.242` |
| **Пароль устройства** | Пароль прибора. С завода — **пустой** |

При отправке формы интеграция:

1. читает `/api/login?device_info` — убеждается, что устройство на месте;
2. выполняет вход (`SHA1("EM-129" + пароль + соль)`) — проверяет пароль;
3. читает MAC-адрес — он становится `unique_id` конфиг-энтри и идентификатором
   устройства (повторное добавление того же прибора блокируется).

Имя устройства берётся из его настройки `user_info` (по умолчанию «EM-129»).

## Опции интеграции

**Настройки → Устройства и службы → Novatek Electro EM-12x → Настроить**

| Опция | По умолчанию | Описание |
|---|---|---|
| Интервал опроса | 30 с | 5–300 с; как часто читаются измерения |
| Синхронизация часов | вкл | раз в час ставить часы прибора по часам HA |
| Страховочное авто-включение | выкл | включать реле обратно после ручного отключения (см. ниже) |
| Задержка авто-включения | 10 мин | через сколько включить (1–1440 мин) |
| Резерв на приборе | 1 сутки | на сколько суток прибор сам удержит реле включённым без HA (1–7 суток) |
| Авто-включение при внешнем отключении | выкл | реагировать на выключение реле **вне HA** (кнопка на приборе) |
| Интервал повторов при внешнем отключении | 10 мин | как часто пытаться включить (1–60 мин); 10 мин — с запасом на загрузку HA (~5 мин) |
| Окно повторов при внешнем отключении | 1 ч | сколько времени повторять (1–24 ч) |

Изменение любой опции перезагружает запись интеграции.

### Смена адреса или пароля (Reconfigure)

Если прибор сменил IP или вы задали/изменили пароль:

**Настройки → Устройства и службы → Novatek Electro EM-12x → ⋮ → Изменить параметры подключения**
(`Reconfigure`) → укажите новый адрес/пароль.

Что происходит:

- проверяется подключение и что это **тот же прибор** (сверка MAC);
- обновляются адрес/пароль, версия прошивки и имя в записи;
- `unique_id` (по MAC) не меняется — **сущности, история и статистика сохраняются**;
- запись перезагружается автоматически.

Если подключился другой прибор (другой MAC) — изменение отклоняется с ошибкой
«Подключённое устройство не совпадает с этой записью».

## Как устроен опрос

- **Измерения** (U, I, P, f, энергия, флаги) — каждый цикл.
- **Настройки** — каждый 5-й цикл и сразу после любой записи через сущность
  (для отклика UI без ожидания следующего опроса).
- **Батч-запросы**: измерения и настройки читаются каждый одной командой
  (`/api/all/get?p1&p2&...` — недокументированная возможность, подсмотренная
  в веб-интерфейсе прибора). Полный цикл: ~0.5 с вместо ~53 запросов.
  Если прошивка не поддерживает батч — автоматический откат на одиночные
  запросы.
- Устройство **однопоточное**: все запросы сериализуются (`asyncio.Lock`),
  соединение закрывается после каждого запроса — так требует прошивка
  (HTTP/1.1 keep-alive подвисает).
- Сессия (`SID`) возобновляется автоматически при истечении.
- Часы: раз в час выполняется `/api/clock/set` с UTC-временем HA
  (прошивка сама прибавляет часовой пояс).

## ⚠️ Одна сессия: конфликт HA и веб-панели

**У прибора только одна активная сессия.** Действует принцип «последний вход
побеждает»: каждый новый логин мгновенно инвалидирует все предыдущие `SID`.
В официальной документации Web API это **не описано** — выявлено экспериментально.

Проверка на реальном EM-129 (три последовательных входа A → B → C):

| Действие | Результат |
|---|---|
| логин A, запрос с A | `200 OK` |
| логин B, запрос с A | **`302 Found`** (A недействителен), B работает |
| логин C | A и B недействительны, работает только C |

**Что это значит на практике:**

- При открытии **веб-интерфейса прибора** его логин выбивает сессию Home Assistant.
  HA обнаруживает `302`, пишет в лог `Session expired … re-logging in` и
  перелогинивается — а это, в свою очередь, выбивает **вашу** открытую панель
  (браузер не перелогинивается сам и падает на экран входа).
- «Приоритет» здесь не прошивочный, а поведенческий: HA перелогинивается
  автоматически каждый цикл (по умолчанию 30 с), поэтому в устойчивом состоянии
  сессию удерживает HA. Это **ожидаемое поведение**, а не ошибка интеграции.
- Пока панель открыта, ответы прибора могут быть медленнее (веб-сервер
  однопоточный): один цикл опроса может занять секунды вместо ~0.1 с.

**Рекомендации:**

- Не держите веб-панель прибора открытой параллельно с HA — они будут
  «перетягивать» единственную сессию друг у друга.
- Для длительной работы с панелью временно **отключите запись интеграции**
  (Настройки → интеграция → ⋮ → Отключить) или увеличьте интервал опроса
  (до 300 с — тогда конфликт реже).
- Всё повседневное делайте через сущности HA, панель — только для диагностики.

## Журналы и события после обрыва связи

При потере связи (проблема в сети **или** перезапуск HA) интеграция при
восстановлении докачивает журналы прибора и публикует пропущенное:

- запоминает последние прочитанные метки времени в `Store` (переживает перезапуск HA);
- при первом контакте и после каждого неудачного опроса читает `syslog` и `loger`;
- события отдаются как **события шины HA** для автоматизаций:

| Событие | Данные | Когда |
|---|---|---|
| `novatek_em12x_syslog` | `timestamp`, `message`, `host`, `entry_id` | каждое новое сообщение syslog (Wi-Fi, облако, SNTP, запуск…) |
| `novatek_em12x_reboot` | `timestamp`, `host` | в журнале есть `SYS: Started …` (перезагрузка/пропадание питания) |
| `novatek_em12x_fault` | `timestamp`, `raised` (биты), `mask` | в данных `loger` появились новые биты ошибок |
| `novatek_em12x_auto_on` | `deadline`, `reason` | сработало страховочное авто-включение |
| `novatek_em12x_billing` | `reason` (manual/reset), `value`, `base_kwh`, `device_wh_at_base` | привязка/корректировка внешнего счётчика |

Диагностика: `sensor.em_129_last_device_event` (время + сообщение в атрибуте),
`sensor.em_129_journal_records_on_reconnect` (сколько записей пришло при последнем
переподключении).

Пример автоматизации на пропадание питания:

```yaml
alias: EM-129 — питание прибора восстановлено
triggers:
  - trigger: event
    event_type: novatek_em12x_reboot
actions:
  - action: notify.mobile_app_phone
    data:
      message: "EM-129 перезагружен (возможно, пропадало питание)"
```

`loger` — это телеметрия раз в 5 минут (напряжение/ток/мощность/температура/
энергия + флаги), `syslog` — журнал событий. Переключения реле в журналы не пишутся.

Имена строятся по правилу «имя устройства + имя сущности»
(`has_entity_name = true`), например `sensor.em_129_voltage`.

| Адрес сервера облака | `cloud_address`, до 32 символов (напр. `my.overvis.com`). **Недоступно** (`unavailable`), пока выключен «Удалённый доступ через облако» |

## Управление устройством

### Реле нагрузки

`switch.em_129_relay` → `/api/utils/ctrl?on|off`. Состояние читается из бита 4
`sys_flag`, т.е. отражает фактическое положение реле независимо от того, кем
оно переключено (панель прибора, HA, защита).

Особенности:

- ручное включение/отключение переводит прибор в **ручной режим** управления
  нагрузкой (бит 7 `sys_flag`);
- при срабатывании защиты реле отключается само и включится обратно по АПВ —
  смотрите бинарные датчики ошибок и сенсор «До повторного включения»;
- если нагрузкой управляет расписание прибора, ручные команды имеют приоритет
  до перевода прибора обратно в режим расписания (с его стороны).

### Защиты и АПВ

Для каждой величины (U, I, P, f) задаются: порог, задержка отключения,
задержка повторного включения и число попыток АПВ. Логика прибора:

1. выход за порог дольше задержки → реле отключается, ставится флаг ошибки;
2. через `задержку АПВ` — попытка включения, если не исчерпан лимит попыток;
3. счётчики попыток сбрасываются через «Сброс счётчиков АПВ» минут без аварий.

Защита по напряжению включена всегда; по мощности и частоте — переключателями.

### Проверка защит и блокировки (на железе)

Проверено на EM-129:

- защита по току: порог временно 1 А, задержка 200 мс, повтор через 2 с,
  **5 разрешённых повторных включений** → после исчерпания прибор **блокируется**:
  реле OFF, `faul_flag` бит 6 (лимит АПВ по току), до этого — бит 4 (порог по току);
- число попыток настраивается (`0` — запрещено, `1–10`, `65535` — всегда), т.е.
  **больше 3-х работает**;
- **снятие блокировки**: ни ожидание `apv_reset_time`, ни `ctrl(True)` не помогают —
  блокировка снимается **перезагрузкой прибора** (кнопка «Перезагрузить устройство»);
- `ar_time` — оставшееся время до повторного включения, **в миллисекундах**
  (в документации ошибочно указаны секунды); сенсор пересчитывает в секунды.
  При **непрерывной** аварии после отсчёта прибор не включает реле, пока авария
  не исчезнет (даже при `count_apv=65535`);
- защита по частоте: пороги выставлялись на границу (hi=lo=50.00 Гц, частота в сети
  колеблется 49.97–50.07 Гц) → срабатывание по верхнему (бит 15) и нижнему (бит 16)
  порогам, `ar_time` — обратный отсчёт в мс; при **непрерывном** выходе за порог
  прибор после отсчёта не продолжает серию включений (ждал возврата частоты),
  поэтому проверить число попыток >3 именно по частоте на стабильной сети нельзя —
  число попыток проверено на защите по току;
- снятие активной аварии: после отключения соответствующей защиты/возврата параметра
  ошибки (`faul_flag`) сбрасываются **без перезагрузки**; блокировка по исчерпанию
  попыток АПВ (бит «лимит») снимается только перезагрузкой;
- защита по напряжению (пороги/АПВ) — проверена частично (использовалась как
  «залипающая» авария для изучения `ar_time`).

Проверка счётчика энергии: при нагрузке ~1.85 кВт (8.25 А) за ~225 с нагрева
счётчик прибора набрал **116 Вт·ч** (ожидаемо ~1.85 кВт × 225 с ≈ 116 Вт·ч) —
учёт корректен, формула внешнего счётчика даёт `база + 0.116 кВт·ч`.

### Режим «отпуск»

Включается переключателем; в период между «Начало» и «Конец отпуска»
нагрузка удерживается отключённой (флаг «управление заблокировано отпуском»).

### Энергия и тарифы

- «Активная энергия» (`total`, кВт·ч) — источник для панели **Energy**;
- суточный/недельный/месячный счётчики (`total_increasing`) — для
  **Utility Meter** или статистики;
- «Тариф» и «Валюта» — настройки тарификации прибора (прибор сам стоимость не отдаёт по API);
- кнопка «Сбросить счётчики энергии» обнуляет **все** счётчики прибора.

### Подключение к панели Energy (учёт стоимости)

1. Настройки → Панели → **Energy**.
2. «Потребление электроэнергии» → **Добавить счётчик** →
   `sensor.em_129_energy_active` (класс `energy`, `total`).
3. В блоке этого счётчика нажмите карандаш → «Стоимость» →
   **«Использовать сущность с текущей ценой»** → выберите
   `sensor.em_129_tariff` (единица `RUB/kWh`, подставляется по валюте прибора).
4. Готово: HA будет считать стоимость по тарифу на момент потребления,
   корректно учитывая изменения тарифа во времени.

Альтернатива для «сколько набежало прямо сейчас» — сенсоры
`sensor.em_129_cost_total` / `cost_daily` / `cost_weekly` / `cost_monthly`
(считаются как `кВт·ч × тариф`, как в веб-интерфейсе прибора).

### Страховочное авто-включение

Защита от ситуации «выключил реле — обесточил сетевое оборудование — приехал на объект».
Включается в опциях (порог + задержка + длительность резерва).

Как работает при отключении реле **через HA** (переключатель «Реле нагрузки»):

1. HA ставит таймер на `задержку` и, параллельно, **событие в расписании прибора**
   (локальное время, `LIVE = длительность резерва`) + `event/run` — резерв сработает,
   даже если HA или её сеть недоступны.
2. На исходе задержки HA включает реле и снимает событие с прибора (возвращая
   сохранённое расписание, если оно было).
3. Если HA была выключена — при старте состояние восстанавливается из `Store`;
   «просроченный» дедлайн отрабатывает сразу (реле включается), а не упускается.
4. Ручное включение (в HA или на объекте) снимает страховку.

#### Полное отключение и пауза на время работ

Обе страховки (для выключения из HA и для внешнего выключения) по умолчанию **выключены**
и включаются только в опциях. Дополнительно есть переключатель
**«Пауза авто-включения»** (`switch.em_129_auto_on_pause`):

- включает «стоп-кран» для **обеих** страховок, ничего не меняя в опциях;
- немедленно отменяет уже взведённый таймер и **удаляет приборное событие-резерв**;
- состояние сохраняется и восстанавливается после перезапуска HA.

⚠️ **Перед работами на электросети обязательно включайте паузу** (или отключайте
опции). Автоматическое включение во время работ — опасность для людей и оборудования.

#### Отключение вне Home Assistant (кнопка на приборе)

На лицевой панели **удержание кнопки ~3 с переключает реле** (короткие нажатия
игнорируются). Такое выключение HA замечает по смене состояния реле и/или по
внеплановой записи в `loger` (прибор пишет её при каждом переключении).

Если включена опция «Авто-включение при внешнем отключении», интеграция:
1. взводит повторы: попытка включения **каждые N минут** в течение окна H часов;
2. параллельно ставит на прибор **резерв**: включение через N минут и далее
   **цепочку дневных событий** на «резерв N суток» (1–7) с перекрытием — реле
   держится включённым непрерывно. События хранятся в памяти прибора и
   **переживают его перезагрузку** — сработают, даже если HA/сеть недоступны
   (проверено на железе);
3. останавливается, как только реле включилось (или по кнопке «Отменить авто-включение»).

Защита от ложных срабатываний: страховка не взводится при срабатывании защит
(`faul_flag`/АПВ) и при собственных командах HA. Если HA перезапускалась и
пропустила момент — переход ON→OFF берётся из `loger`, если он был не позже окна H.

**Важно про сценарий «сеть запитана через реле».** Если роутер/точка доступа
питаются от нагрузки прибора, то при выключенном реле **HA физически не может
достучаться до прибора** — повторы со стороны HA в этот момент бесполезны.
Восстановление обеспечивает именно **внутреннее событие прибора**: оно включает
реле по своим часам и удерживает его. Когда сеть поднимется, HA переподключится и
снимет резерв, переведя реле в ручной режим. Повторы HA каждые N минут полезны в
случае, когда прибор доступен (например, сеть не через реле или уже загрузилась).

Ограничения:
- приборный резерв работает до `N суток` (максимум 7; если HA так и не вернулась,
  после этого реле отключится);
- резерв на несколько суток опирается на **ход часов прибора без питания**. Проверено:
  часы сохраняют время минимум **15 минут** без питания и без NTP (уход 0 с), события
  переживают перезагрузку. Насколько хватает резерва RTC на сутки — ещё не проверено
  (планируется длинный тест); при очень долгом обесточивании цепочка может
  «промахнуться» по времени (макс. 24 ч) — если HA не вернётся
  за это время, реле снова отключится;
- если на приборе уже есть своё расписание, событие-резерв не создаётся
  (чтобы не затирать пользовательское), остаётся только таймер HA — при живом HA
  этого достаточно;
- при отключении **не через HA** (кнопкой на объекте, по защите) страховка не взводится.

Сущности: `sensor.em_129_auto_on_at`, `button.em_129_cancel_auto_on`.

### Внешний (биллинговый) счётчик

Перед прибором стоит сертифицированный счётчик, чьи показания подаются в
энергокомпанию, а собственный счётчик EM-129 имеет другое начальное значение.
Интеграция умеет показывать расход «как если бы это был внешний счётчик».

Формула: `показание = база + (счётчик_прибора_сейчас − счётчик_прибора_на_базе) / 1000`.

- **Одно поле** `number.em_129_set_external_meter_reading` выполняет и первичную
  привязку (ввести фактическое показание при монтаже), и периодическую
  **корректировку** (ввести текущее показание энергокомпании). Это одна и та же
  операция перепривязки к текущему счётчику прибора.
- Сенсор `sensor.em_129_external_meter_reading` показывает расчётное показание
  (кВт·ч, `total`); атрибуты: `base_kwh`, `device_wh_at_base`, `updated_at`.
- **Сброс счётчика прибора** (кнопка «Сбросить счётчики энергии», сброс прибора)
  обрабатывается автоматически: база пересчитывается так, чтобы внешнее показание
  не «прыгнуло» назад; в шину отправляется событие `novatek_em12x_billing`
  (`reason: reset`). Ручная привязка — `reason: manual`.
- Состояние хранится в `Store` и переживает перезапуск HA. Коэффициент (ТТ/ТН)
  пока не поддерживается.

### Часы

Три механизма, приоритет у последнего сработавшего:

1. встроенная коррекция хода («Коррекция хода часов»);
2. SNTP-клиент прибора (адрес/порт/период + переключатель);
3. синхронизация из HA — раз в час, если включена в опциях.

## Устранение неполадок

| Симптом | Причина и решение |
|---|---|
| «Не удалось подключиться» при добавлении | устройство недоступно по IP; проверьте `http://<ip>/api/login?device_info` в браузере |
| «Ошибка аутентификации» | неверный пароль прибора (сменили на панели?) — укажите новый в опциях |
| Сущности стали unavailable | пропала связь / устройство перезагружается; интеграция восстановит сессию сама |
| Долгий отклик записей настроек | нормально: команды сериализуются, прошивка однопоточная |
| Часы прибора «убежали» на часовой пояс | включите синхронизацию в опциях; сенсор «Время устройства» уже учитывает TZ прибора |
| Устройство не отвечает после смены настроек сети | сетевые параметры (`wifi_*`, `dns1/2`) намеренно не экспортируются — меняйте их через веб-интерфейс прибора |
| Сменился IP-адрес прибора | Настройки → интеграция → ⋮ → «Изменить параметры подключения» (reconfigure), без удаления записи |
| В логе `Session expired … re-logging in` при открытой веб-панели | нормально: у прибора одна сессия, HA перелогинивается и «забирает» её (см. раздел «Одна сессия») |

## Безопасность

- Устройство общается по **открытому HTTP** — не выставляйте его в интернет.
- Пароль по умолчанию пустой: установите пароль на приборе и пропишите его
  в опциях интеграции (хранится в `entry.data` конфигурации HA).
- Устройство **не проверяет диапазоны** записываемых значений — все границы

### Проверено на реальном устройстве (EM-129)

Все команды чтения и записи прогнаны на живом приборе (кроме сетевых `wifi_*`, `dns1/2`):

- чтение: все 55+ параметров, журналы `loger`/`syslog`, расписание `event`
- запись: 38 параметров round-trip, реальные изменения порогов/тарифа/яркости с откатом
- управление: реле `ctrl on/off` (бит 4 `sys_flag`), `enrgrst`, `clock/set`, `clock/sync`,
  `event/set`/`event/delall`, `loger/delall`, `syslog/delall`, `reboot` (с ожиданием возврата)

Все расхождения между официальной документацией и фактическим поведением
прибора собраны в разделе
[«Источники и расхождения с документацией»](#источники-и-расхождения-с-документацией).

### Поведение при пропадании питания (проверено)

- **RTC без питания:** часы сохраняют время минимум **15 минут** без питания и без NTP
  (дважды проверено: простой ~14–15 минут, уход 0 с, флаг «неисправны часы» не поднимался).
- **Состояние реле после возврата питания:** прибор восстанавливает **последнее**
  состояние — было ON → ON, было OFF (выключено кнопкой) → OFF.
- **События расписания переживают перезагрузку** прибора, в том числе реальное
  пропадание питания (`PORR=1`), и срабатывают в назначенное время после возврата
  питания (проверено: событие, поставленное на +20 мин, сработало по часам после
  ~14-минутного обесточивания).
- После power-on (`SYS: Started … [PORR=1]`) сеть/Wi-Fi поднимается самостоятельно
  (≈7 с), независимо от состояния реле.

| Команда | Описание | Используется интеграцией |

| `/api/all/get?p1&p2&...` | пакетное чтение нескольких параметров | да — основной режим опроса |
| `/api/settings/set?p1=v1&p2=v2` | пакетная запись (атомарная: при невалидном параметре отклоняется весь батч) | нет (сущности пишут по одному) |
| `/api/firmw/fwinfo` | версия прошивки (`CUR_VERSION`), проверка обновлений | да — версия в карточке устройства |
| `/api/firmw/fwupdate` | загрузка прошивки (POST) | нет — намеренно |
| `/api/utils/cloud_info` | детальный статус облака my.overvis.com | да — 3 diagnostic-сенсора (каждый 5-й цикл) |
| `/api/utils/evt_info` | ближайшее/следующее событие расписания | нет |
| `wifi_wdt_enable` | сторожевой таймер Wi-Fi | да — переключатель настроек |

### Ограничения

- Чтение журналов (`loger`, `syslog`) и расписания (`event`) доступно в API,
  но сущностями не экспортируется (план на следующие версии).
- Настройки Wi-Fi и DNS не экспортируются намеренно — смена сети через HA
  может разорвать связь с устройством.
- EM-126T-специфичные параметры (`load_type`, `temp_corr`, `temp_hys`) не экспортируются.
- Режим расписания прибора (`event/set`/`event/run`) не экспортируется.

### Расхождения: документировано vs фактическое поведение

| # | В документации | Фактически на EM-129 | Как учтено |
|---|---|---|---|
| 1 | Строковые настройки (`user_info`, `sync_sntp_address`, `cloud_address`) — **base64** | **HEX** (напр. `6d792e6f7665727669732e636f6d` = `my.overvis.com`) | `decode_setting_str`/`encode_setting_str` в `api.py` |
| 2 | `clock/set?sec=` — UNIX-время | принимает **UTC**, прибор сам прибавляет `time_gmt` (эпоха смещена на часовой пояс) | отправляем UTC; сенсор времени вычитает `time_gmt` |
| 3 | `volt_rms` — «текущее напряжение» | команда отсутствует (`SINTAXIS_ERROR`) | используется `volt_msr` |
| 4 | Диапазоны значений при записи | **не проверяются** (`led_intens=99` принимается) | границы держат number-сущности HA |
| 5 | `event/set` дубликат → `ERROR_ALREADY_EXISTS` | дубликат принимается без ошибки | не полагаемся на этот статус |
| 6 | Конец журнала данных — `EOSL` | `loger` возвращает **`EOL`** (у `syslog` — `EOSL`) | статусы трактуются как «конец» |
| 7 | `device_id`: 243=EM-125, 293=EM-126T, 273=EM-129 | EM-129 отдаёт **271** | в `MODEL_NAMES` добавлен 271 |
| 8 | Пакетное чтение/запись нескольких параметров — **не документировано** | работает (`/api/all/get?p1&p2…`, `set?p1=v1&p2=v2`, запись атомарная) | основной режим опроса |
| 9 | Стоимость электроэнергии | в API **нет**; вычисляется веб-интерфейсом как `кВт·ч × тариф` | сенсоры `tariff`/`cost_*` считают то же в HA |
| 10 | Одновременные сессии/лимит клиентов | **одна сессия**, «последний вход побеждает» (302 у прежних) | автоматический релогин; см. раздел «Одна сессия» |
| 11 | Способ обнаружения в сети | mDNS/zeroconf **не поддерживается** (5353/udp закрыт), SSDP не найден | добавление по адресу/имени |
| 12 | `ar_time` — «время в секундах» | **в миллисекундах** (напр. 4481 при задержке АПВ 5000 мс) | сенсор делит на 1000 и показывает секунды |
| 13 | `firmw/fwinfo`, `firmw/fwupdate`, `utils/cloud_info`, `utils/evt_info`, `wifi_wdt_enable` — **не документированы** | реализованы в прошивке (найдены в веб-интерфейсе) | см. таблицу «Недокументированные возможности» |

Если ваш прибор ведёт себя иначе (другая прошивка/модель) — заведите issue с логом
`custom_components.novatek_em12x: debug`.
